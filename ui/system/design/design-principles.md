# Design Principles for Sekai UI System

Version: 1.0
Style: Notion-style Minimal UI

This document defines the design principles used in **Sekai UI System**.

The goal of these principles is to ensure that all UI generated by humans or AI agents remains consistent, calm, readable, and reusable.

---

# 1. Design Philosophy

Sekai UI System follows a **Notion-style minimal interface philosophy**.

The system prioritizes clarity, calmness, and usability over visual decoration.

The interface should feel:

- calm
- readable
- professional
- distraction-free
- consistent across applications

The system must work well for:

- dashboards
- SaaS applications
- CRUD interfaces
- analytics tools
- AI applications

Visual hierarchy is established through spacing and typography, not through decoration or color.

# 2. Color Usage Rules

Colors must follow the definitions in `design/tokens.json`.

Rules:

- `color.bg` is the page/root canvas background — applied to `<body>` and full-page containers. Must remain white (`#FFFFFF`).
- `color.surface` is the component surface background — applied to cards, inputs, dropdowns, modals, and any elevated UI element. Also `#FFFFFF` but semantically distinct from the page background.
- Subtle backgrounds use `color.bg_subtle` for secondary areas, sidebars, and section separators
- Borders and separators use `color.border` for standard lines and `color.border_strong` for emphasized dividers
- Body text uses `color.text`; supporting text uses `color.text_muted` or `color.text_subtle`
- The primary accent color (`color.primary`) must be used sparingly — reserved for primary actions and active states. Use `color.primary_hover` exclusively for the hover state of primary-colored interactive elements (primary buttons, active links).
- Status colors (`color.success`, `color.warning`, `color.danger`) appear only when communicating state to the user
- `color.primary_subtle` (`#EEF4FF`) is used for focus rings and light primary backgrounds (e.g. `focus:ring-sekai-primary-subtle`)
- `color.danger_subtle` (`#FEF2F2`) is used for focus rings and light danger backgrounds (e.g. `focus:ring-sekai-danger-subtle`, `hover:bg-sekai-danger-subtle`)

Avoid:

- multiple accent colors within a single view
- bright or saturated colors for decoration
- using color as the only indicator of meaning (always pair with text or icons)
- gradients of any kind
- neon or high-saturation tones

# 3. Typography Rules

Typography is the primary method of creating hierarchy in the UI.

Font family is defined in `design/tokens.json` under `font.family` and defaults to Inter with system-ui fallbacks.

Standard hierarchy:

| Level    | Token           | Value | Usage                         |
|----------|-----------------|-------|-------------------------------|
| Title    | `font.size_xl`  | 24px  | Page titles, modal headings   |
| Subtitle | `font.size_lg`  | 20px  | Section headings, card titles |
| Body     | `font.size_md`  | 16px  | Primary body text             |
| Small    | `font.size_sm`  | 14px  | Labels, table cells, captions |
| Caption  | `font.size_xs`  | 12px  | Metadata, timestamps, hints   |

Line height tokens:

| Token                    | Value | Usage                                  |
|--------------------------|-------|----------------------------------------|
| `font.line_height_tight`   | 1.3   | Titles and large headings              |
| `font.line_height_normal`  | 1.4   | Compact UI — labels, captions, badges  |
| `font.line_height_relaxed` | 1.6   | Body text and longer prose             |

Font weight tokens:

| Token                   | Value | Usage                              |
|-------------------------|-------|------------------------------------|
| `font.weight_normal`    | 400   | Body text, table cells, captions   |
| `font.weight_medium`    | 500   | Labels, subtitles, nav items       |
| `font.weight_semibold`  | 600   | Titles, headings, critical labels  |

Note: The `leading-tight`, `leading-normal`, and `leading-relaxed` Tailwind classes in this system are intentionally overridden in `tailwind.config` to match the token values above (1.3, 1.4, 1.6). They do not use Tailwind's built-in defaults.

Rules:

- Do not introduce font sizes, weights, or line heights outside the defined token scale
- Use `font.weight_semibold` for titles and headings only; use `font.weight_medium` for emphasis within body
- Text must remain readable against all defined background colors

# 4. Spacing Rules

Spacing is one of the most important design tools in Sekai UI System.

Spacing creates hierarchy, breathing room, and visual separation between elements.

All spacing values must follow the scale defined in `design/tokens.json` under `spacing`.

Standard spacing scale:

| Token        | Value | Typical usage                     |
|--------------|-------|-----------------------------------|
| `spacing.2`  | 8px   | Tight inner padding, icon gaps    |
| `spacing.3`  | 12px  | Small component padding           |
| `spacing.4`  | 16px  | Standard component padding        |
| `spacing.5`  | 20px  | Medium gaps between elements      |
| `spacing.6`  | 24px  | Section padding, card padding     |
| `spacing.8`  | 32px  | Between sections                  |
| `spacing.10` | 40px  | Large layout gaps                 |
| `spacing.12` | 48px  | Major section separators          |

Micro-spacing exception:

Some sub-component internals use Tailwind's built-in fractional spacing values (`gap-0.5` = 2px, `py-1.5` = 6px, `mt-0.5` = 2px) for tight visual density within compact elements such as navigation items and card subheadings. These are intentional and do not violate the spacing scale — they apply within the internal structure of a component, not between layout sections.

Rules:

- Use larger spacing values between major layout sections
- Use smaller spacing values for compact components like form rows and table cells
- Maintain consistent spacing between similar elements — never vary arbitrarily
- Spacing should do the work of separating content, reducing the need for borders or shadows

# 5. Layout Principles

Most application pages follow a consistent three-part structure:

```
Topbar
Sidebar
Main Content
```

This structure is implemented via `layouts/app_shell.html`.

Layout constants are defined in `design/tokens.json` under `layout`:

| Token                      | Value   |
|---------------------------|---------|
| `layout.sidebar_width`    | 240px   |
| `layout.header_height`    | 56px    |
| `layout.content_max_width`| 1200px  |

Rules:

- The sidebar width must remain fixed at the token value
- The main content area must not exceed `content_max_width`
- The topbar height must follow `header_height`
- Do not create new layout structures unless a use case cannot be served by the standard shell
- Auth pages (login, register, password reset) use `layouts/auth.html`, which centers a narrow card on the page

# 6. Component Design Principles

All components must follow these principles.

## Simplicity

Each component must have a single clear responsibility. Avoid components that try to do too much.

Avoid:
- complex nested logic within a component
- excessive configuration options
- unnecessary variants

Prefer small, composable components over large monolithic ones.

## Reusability

Components must be reusable across different page types including dashboards, list pages, forms, and configuration panels.

Before creating a new component, always check the `components/` directory for an existing one that can be reused or extended.

## Consistency

All components must follow:

- `design/tokens.json` for all visual values
- the spacing scale for padding and margin
- the typography scale for text sizes
- the color definitions for backgrounds, borders, and text

Hardcoded color, spacing, or size values must be avoided.

## Border and Shadow Usage

Borders should be subtle. Use `color.border` as the default and `color.border_strong` only for emphasis.

Shadow usage must remain minimal:

- `shadow.sm` is allowed for floating cards and modal dialogs
- `shadow.none` is the default for most components

Avoid heavy drop shadows and layered shadow effects.

## Radius Usage

Border radius values are defined in `design/tokens.json` under `radius`. Select the appropriate size based on component type:

| Token       | Value | Typical usage                             |
|-------------|-------|-------------------------------------------|
| `radius.sm` | 6px   | Inputs, tags, badges, table cells         |
| `radius.md` | 8px   | Buttons, cards, dropdowns, tooltips       |
| `radius.lg` | 10px  | Modals, large panels, sheet containers    |

Do not mix radius sizes arbitrarily within a single component family.

## Interaction Feedback

Interactive elements should provide subtle, fast feedback:

- background color change on hover using `color.surface_hover`
- focus ring on inputs and buttons using the primary color
- no large motion effects or transitions exceeding 150ms

## Accessibility

Components must maintain basic accessibility standards:

- sufficient contrast between text and background
- readable font sizes (minimum `font.size_sm`)
- visible focus states on all interactive elements
- clickable targets large enough for interaction
- semantic HTML elements used appropriately

# 7. AI-Friendly Design

Sekai UI System is designed for AI-assisted development.

This means:

- simple and predictable component structure
- consistent naming across files and tokens
- reusable layouts that reduce generation complexity
- minimal design complexity that reduces error surface

These rules help AI agents generate consistent UI without introducing unexpected visual variations.

When an AI agent is generating or modifying UI:

1. Read `docs/sekai-ui-system-spec.md`
2. Read this file (`design/design-principles.md`)
3. Read `design/tokens.json`
4. Check existing components in `components/`
5. Reuse components whenever possible
6. Create new components only when necessary
